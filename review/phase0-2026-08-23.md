### R-02 — the complaint mutation is never applied (`scripts/mutation_check.sh:39,50`)

**Severity: high.** This is the single most important mutation in the file —
it neuters `assertNoComplaintSignal` — and it is a no-op.

Line 39 builds the entry with `$'...'` ANSI-C quoting, so the `\n` in the
replacement becomes a **real newline**. Line 50 then does:

```sh
IFS=$'\t' read -r name file needle replacement <<<"$entry"
```

`read` consumes one line. The embedded newline truncates `replacement` at
exactly the point where the mutation begins, leaving:

```
needle      = [export function assertNoComplaintSignal(record: unknown, where: string): void {]
replacement = [export function assertNoComplaintSignal(record: unknown, where: string): void {]
```

Needle equals replacement. The Python helper's `text.count(needle) != 1` check
passes, it substitutes identical text, the file is unchanged, the suite passes,
and the script reports `SURVIVED`.

Reproduction: `review/artifacts/read-truncation-repro.txt`.

**The tests are fine.** I applied the mutation the script *intended*:

```python
t.replace(n, n + "\n  if (record !== undefined || where !== undefined) return;")
```

Result: **5 tests failed** (`planner.test.ts` blocks at lines 123-142 and
367-390). The safety net catches it. Only the harness is broken.

**Suggested fix** (not applied): give `read` an explicit delimiter, e.g.
`IFS=$'\t' read -r -d '' name file needle replacement <<<"$entry"`, and drop
the now-redundant `.replace("\\n", "\n")` in the Python helper — or keep the
replacement single-line by anchoring on the function body's first statement
instead of its signature. Either way, add a self-test that asserts
`needle != replacement` for every entry before running the suite; that one
assertion would have caught this.

### R-03 — the other two survivors are equivalent mutants

**Severity: medium.** These cannot be killed by any test, so
"add a test that fails for each, then re-run" is unsatisfiable as written.

**`shipped: a coordinator lock loses to the computed value`** —
`locks.get(id) ?? unlockedHours.get(id) ?? 0` → `unlockedHours.get(id) ?? locks.get(id) ?? 0`.
`unlockedHours` is built from `shares`, which is built from
`unlocked = areas.filter(a => !locks.has(a.id))` (`app/src/lib/planner.ts:60,72-86`).
A locked area id is therefore *never* a key in `unlockedHours`, so
`unlockedHours.get(lockedId)` is always `undefined` and `??` falls through to
the lock. The swap is a no-op by construction.

Empirically: 2,988 feasible inputs — 1-4 areas, every lock subset, lock values
{0,5,8,20,40}, budgets {0,8,40,80,120,400}, floors {0,4,8,20}, with and without
a phantom lock on a non-existent area — **0 produced different output**.

**`shipped: budget-conservation check disabled`** —
`if (allocatedTotal !== normalizedBudget)` → `if (false && ...)`. This branch
is a post-condition assertion. On correct code it is unreachable, so removing
it is undetectable through the public API. Empirically: 4,119 feasible plans
across budgets 0-300, floors {0,1,4,8,20}, and three load vectors including
all-zero and near-zero loads — **0 violated budget conservation**.

Harness: `review/attacks/equivalence.attack.test.ts`.

**Suggested fix** (not applied): drop both entries, or replace them with
mutations that are actually observable. For the lock one, mutate the
`unlocked` filter itself (`!locks.has` → `locks.has`) — that *is* observable.
For the conservation check, mutate what it protects rather than the check:
e.g. change `remaining` to `remaining - 1` and confirm a test notices.
Leaving unkillable mutants in a required gate trains people to ignore it.

## R-06 — `lib/contracts.ts` is dead code and F-1 does not list it

**Severity: medium.** File: `app/src/lib/contracts.ts`, 28 tests in
`app/src/lib/contracts.test.ts`.

I built the complete non-test import graph from `main.tsx`:

```
main.tsx → App.tsx → { data/digitizationAudit, lib/demo, lib/intervention, lib/planner }
```

Nothing else is reachable. `lib/contracts.ts` is imported only by its own test.
Its `parseObservationsV0`, `parseQualityReportV0`, and `assertNoPreciseFields`
never run in the product. Confirmed against the built artifact: no
`assertNoComplaintSignal`, `service_request`, `call_volume`, or
`complaint volume may never influence` string appears in `app/dist/assets/index-*.js`.

F-1 correctly names `domain/planner`, `PlannerPanel`, and `ResponsibleDataCards`.
It does not name `lib/contracts.ts`, and that omission matters because
`assertNoPreciseFields` is a *privacy* check the reader would reasonably assume
runs client-side. It does not. (The Python privacy scan in
`pipeline/src/stillhere_pipeline/privacy.py` does run, over the built bundle,
in CI — so the privacy promise is not unguarded. But it is guarded in one place,
not two.)

## What I tried that did **not** break it

Stated so the build session knows what is genuinely covered, not just what failed.

- **The characterization suite is real.** 7 of the 10 mutations were caught,
  and the 3 that were not are explained above — none of them is a coverage
  hole. The suite fails when the planner is wrong.
- **The complaint guard itself is correctly written, within its design.** It
  recurses into nested objects (`planner.ts:67-71`, with a comment recording
  the earlier one-level bug) and into arrays (`:53-56`). Attack A and the
  nested/array variants are all refused. I could not find a *name-shaped*
  complaint field that slips past it.
- **Budget conservation genuinely holds.** 4,119 feasible plans, zero
  violations. The invariant is real; only the mutation testing it is ill-posed.
- **The privacy scan does fail closed.** `--require-bundle` turns a missing
  `app/dist` into an error, and `verify.sh` orders the scan after the build.
  I confirmed F-1's non-finding here rather than taking it on trust.
- **`App.tsx` has axe coverage on the shipped shell.** I initially expected
  a11y coverage to be zero because `PlannerPanel.a11y.test.tsx` grades a
  component that does not ship. That inference was wrong: `App.test.tsx`
  contains four axe assertions over the deployed shell (initial state, after
  the full decision flow, guide panel open, workspace view). Recording the
  correction so nobody repeats it.
- **The DSDP transcription arithmetic is exact.** 959 + 133 = 1,092 and
  841 + 114 = 955, reconciling the project-derived six-area core to the
  publisher's seven-area total in both months, as
  `tests/pipeline/test_monitoring_data.py:102-125` asserts.
- **The suite passes cleanly in isolation.** 181/181 in a fresh worktree with
  its own `node_modules`. No hidden ordering or environment dependence found.
